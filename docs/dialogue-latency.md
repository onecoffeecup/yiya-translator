# 对白延迟排查（2026-10-08）

玩家反馈升级后约 3～4 秒才出现译文。该时间是端到端等待，尚无玩家的 OCR / HTTP 分段耗时及接口配置，不能据此认定她的模型开启了推理，或认定全部等待都由 OCR 引起。

## 已复现的问题与修复

- 正式 0.2.1 build 17 默认每 1.2 秒采样一次，再做两帧稳定确认；高相似真实修正需三帧。玩家界面没有挂载识别间隔控件。对白 timer 已改为 0.5 秒，在启动、重建 timer 及自动模式切换时统一使用。界面模式保留原配置周期，准确 OCR、两帧 / 三帧确认、去重、身份与缓存规则保留。
- 请求原先根据普通「模型名」判断是否关闭 DeepSeek 推理，没有使用实时请求实际选中的模型。在通用第三方接口上，普通模型为其它模型而实时模型为 DeepSeek 时，实际请求漏掉 `thinking: disabled` / `reasoning_effort: none`；反向配置则给其它实时模型误加这些字段。现在按最终请求 URL 和最终请求模型判断。

第二项配置问题是可复现的请求构造缺陷，尚未确认反馈玩家采用了这种配置。对比 v0.2.0 与 v0.2.1，实时模型选择及请求模块原本一致；不是把语法的「深度复核」接到了对白上。

采样周期变短减少程序固定等待，不保证所有机器都能在 0.5 秒完成 OCR，也不保证接口在固定时间返回。`inFlight` 仍防止任务重叠；长翻译请求期间不采新帧的既有缺口仍存在。

## 最短现场核对

用本轮候选包保持同一输入源、同一场景及同一实时模型，翻过三句对白，核对译文出现时间与「最近识别」「翻译耗时」。优先使用「运行设置 → 诊断与反馈」导出的无文字元数据确认 OCR 和 HTTP 耗时；需要文字或画面证据时另由用户明确启用。

现有 API Key 的读取仍只匹配 `CFBundleShortVersionString`；本轮只增加 build 时继续复用玩家自己的 0.2.1 本机 Key。不要把凭据或设置文件作为体验反馈发送。
