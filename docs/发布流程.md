# 维护者发布流程

当前版本作为 Pre-release 发布。完成本机检查后仍需由另一台 Mac 记录首次安装结果，不宣称跨机器现场验收已通过。

## 本机准备

```bash
python3 scripts/reference-data.py check
scripts/run-checks.sh
scripts/release-app.sh
python3 scripts/reference-data.py pack
python3 scripts/package-source.py
```

`release-app.sh` 默认重新构建双架构，组装完整词典、许可与使用说明，并在压缩后解压回验签名、二进制 UUID、资料及文档的一致性。旧的同名下载包备份到 `.build/release-backups`。

Release 附件：

| 文件 | 用途 |
| --- | --- |
| `yiya-0.2.0.zip` | 普通试用者下载，App 内已包含词典 |
| `fuyi-reference-20261004.zip` | 从源码构建时使用的独立资料快照 |
| `fuyi-source-0.2.0.zip` | 筛选过的公开源码包，不包含大型数据库或本机材料 |
| 对应的 `.sha256` 文件 | 核对下载完整性 |

公开源码包使用明确的目录清单，仅收录源码、脚本、测试、文档、图标和来源许可；会排除凭据文件、私人目录、交接、设计探索、缓存及数据库，并检查常见 token / 私钥特征。扫描不能代替人工确认将要公开的内容。

## 验证干净源码

把源码包解压到一个新目录，然后用独立资料附件执行 `reference-data.py install`。从该目录运行双架构构建和 `run-checks.sh`，确认不依赖原目录的 `.build`、设计截图或私人材料。

## GitHub 发布

1. 检查 README、许可和待公开文件列表。源码采用 MIT，第三方资料许可分别保留。
2. 提交公开文件并推送到选定的仓库；大型 SQLite 不加入普通 Git 历史。
3. 创建版本标签和 GitHub Release，勾选 **Set as a pre-release**，使用 `docs/发布说明.md` 的正文并上传以上附件及校验文件。
4. 从实际发布链接重新下载，在另一台 Mac 按 `docs/首次安装验收.md` 检查。
5. 根据实际反馈更新已知问题和发布说明；完成前不把未验证项目标为通过。

若用户明确选择覆盖已经发布的 `v0.2.0` 附件，先在新提交上完成全部检查与打包，再将同名标签移至新提交，并替换 Release 的六个附件和说明。标签变更后，GitHub 自动提供的源码压缩包也应与手工提供的源码附件对应；上传后从远端核对标签提交、附件大小和 SHA-256。旧下载包仍可能在使用者本地缓存，因此发布说明要注明同名附件已更新。

源码仓库及下载附件的排除策略不删除本机交接、私人资料或学习数据。
